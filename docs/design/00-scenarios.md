# 场景分析：我如何使用 agent 干活

> 状态：已确认 · 更新：2026-08-08
> 本文是 paihuo 会话/工作区重构设计的出发点。回答一个根本问题：**我到底怎么用 agent 干活，三种工具形态（ssh+tmux / pi-web / paihuo）各自适合什么。**

## 1. 场景全景

按两个维度切：**人在回路程度**（实时交互 ↔ 无人值守）× **任务形态**（一次一问 ↔ 批量流水线）。共 8 个场景：

| # | 场景 | 特征 | 人在回路 |
|---|---|---|---|
| 🅰 | 结对探索（交互式） | "帮我看看这个 bug 在哪"——答案不确定，边走边讨论，回合制 | 全程 |
| 🅱 | 单任务交付 | "实现这个功能"——需求相对明确，期望完整交付 | 下发+验收 |
| 🅲 | 批量任务并行派发 | "这 20 个 issue 都给我干了"——不等单个完成，一次性下发，后台持续跑 | 下发+抽查 |
| 🅳 | 多角色分工 | codex 干 Rust 重构、claude 干前端——不同 agent × skills × 配置 | 人肉编排 |
| 🅴 | 定时 / 无人值守 | 每天跑测试、定期代码审查、夜间接任务 | 无 |
| 🅵 | 审查验收 | agent 交付代码 → 人审查 diff → 通过/驳回。批量下发时风险放大，审查是安全阀 | 把关 |
| 🅶 | 失败恢复 / 续跑 | 任务挂了/被打断，要能重试、续跑、保留上下文；日志留档 | 事后 |
| 🅷 | 多端远程访问 | 手机/平板/办公室电脑，随时看进度、操作 | — |

## 2. 三种形态的本质定位

| 形态 | 一句话定位 | 本质 |
|---|---|---|
| ssh + tmux + CLI | 原始组合 | 什么都能干，但**一切自己管**（会话、日志、并发、恢复） |
| pi-web | 远程持续会话工作台 | 把 agent 当**结对程序员**（同步、交互、会话连续） |
| paihuo | 异步任务调度平台 | 把 agent 当**团队**（异步、批量、流程化、把关） |

## 3. 场景 × 工具匹配矩阵

| 场景 | ssh+tmux | pi-web | paihuo | 最佳 |
|---|---|---|---|---|
| 🅰 结对探索 | 🟡 能，易断 | ✅✅ | 🟡 别扭（现状） | **pi-web** |
| 🅱 单任务交付 | 🟡 能 | ✅ | ✅ | 都行 |
| 🅲 批量派发 | 🟡 原始 | 🟡 无任务语义 | ✅✅ | **paihuo** |
| 🅳 多角色分工 | 🟡 脑内管理 | ❌ 单 agent | ✅✅ | **paihuo** |
| 🅴 定时无人值守 | 🟡 手写 cron | ❌ | ✅✅ | **paihuo** |
| 🅵 审查验收 | 🟡 自己 diff | 🟡 有查看无流程 | ✅ 有流程差体验 | **paihuo（需补）** |
| 🅶 失败恢复 | 🟡 看窗口在不在 | 🟡 无任务语义 | ✅✅ | **paihuo** |
| 🅷 多端访问 | ❌ 体验差 | ✅ | ✅ | pi-web / paihuo 等价 |

## 4. 关键洞察

1. **paihuo 甜蜜区 = 🅲🅳🅴🅵🅶**——"流程化地把 agent 当团队用"。pi-web 甜蜜区 = 🅰（交互协作）。**两者互补，不是替代关系**。
2. **paihuo 走的是 pi-web 不会走的路**：pi-web 解决"一个 agent 的会话连续性"，paihuo 解决"多个 agent 的**任务生命周期**"（创建→执行→审查→合并→恢复）。
3. **🅵 审查验收是甜蜜区里唯一的短板**：有审批流程但审查体验差（纯文本 diff）——这是 diff 可视化审查需求（R1）排在第一位的原因。
4. **多角色分工目前是人肉编排**：未来纵深是 agent 间自动编排（源任务成功 → 自动派合并任务已是雏形）。
5. **🅷 多端访问不是差异化**：是基础能力，不是卖点。

## 5. 用户补充的关键约束（2026-08-08 讨论确认）

- **简单问题** → 直接下发一个任务（批处理，现有模型）
- **复杂问题** → 需要与 agent 多轮交互，逐渐分析清楚，然后执行，执行完可能还要调整
- **冲突问题**：同一项目上两种模式会打架。paihuo 通过 worktree 给每个任务隔离，批量任务互不打架；但 **pi-web / ssh 的默认交互式没有 worktree**，会与 paihuo 任务冲突
- **结论**：希望两种方式兼容——**所有干活方式统一进 paihuo，交互式也走 worktree 隔离**
- **skills 痛点**：skills 太多，不同 skills 适用场合不同，希望按任务类型加载不同 skills，手动管理太麻烦
- **pi-web 最好的点**：整个 web UI 和 pi agent 的深度集成
- **远期**：agent 自动编排派发，以 pi 作为核心 agent 定制化（pi 可嵌入、可编程、有 skills/plugins 机制）
