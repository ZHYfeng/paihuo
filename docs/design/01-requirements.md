# 需求分析 v2：paihuo 会话与工作区重构

> 状态：已确认 · 更新：2026-08-08
> 前置：`00-scenarios.md`（场景分析）。本文定义产品方向与需求全景。

## 1. 产品定义（确认版）

> **paihuo = 项目级 agent 工作平台，所有干活的唯一入口**
> - **简单问题** → 批量任务（现有模式）
> - **复杂问题** → 常驻交互会话（pi-web 式），**全部走 worktree 隔离，干完交付转为任务**
> - **pi 为核心 agent**（RPC 深度集成，消息流级 UI）；codex/claude 次之（终端级 UI，显示效果不如 pi web 的终端属可接受降级）

## 2. 现状事实核查（2026-08-08 代码确认）

| 事实 | 结论 |
|---|---|
| 交互任务已有 worktree（`executor.go:708`） | paihuo 内部任务不打架；真正没解决的是 paihuo **外部**的干活方式（pi-web/ssh 直接开 agent 没有 worktree） |
| 交互任务绑定任务生命周期（/exit 即结算） | 复杂问题"多轮交互→执行→调整→再执行"被硬切成一轮轮任务，缺"挂起不结算"概念 |
| SKILL.md frontmatter 解析出 tags（`handlers.go:1872`） | 有 tags 但**零自动匹配**，技能选择是角色级手动勾选 |
| 任务创建表单无技能选项 | 任务级技能选择完全缺失 |
| pi 有官方 RPC 模式（`pi --mode rpc`，JSONL 全双工） | **pi 会话可拿到结构化消息流**（不是终端式），Go 后端可直接驱动 |
| pi RPC 有 `switch_session` 命令 | 运行中进程可切换会话文件，恢复会话无需重启进程 |
| `workspace.Ensure` 对已存在 worktree 直接返回 | 会话交付后任务可**复用会话 worktree**，合并流程零改动 |

## 3. 核心新实体：会话（Session）

与任务**平行**的一等公民。生命周期：

```
创建会话（项目+角色+worktree）
  → 活跃（agent 进程跑着，对话中）
  → 挂起（agent 进程退出，worktree+会话保留，不结算不占并发槽）
  → 恢复（拉起 agent，继续对话）
  → 交付（转为任务：引用会话，走现有审批→合并→结算流程）
```

| 属性 | 需求 |
|---|---|
| 隔离 | git 项目自动 worktree（`paihuo/session-<id>`），与任务分支互不打架 |
| 会话数据 | pi 会话文件（JSONL transcript）+ 输入历史，存 paihuo 管理的会话目录 |
| 挂起 | 释放内存/并发槽；worktree 与 transcript 保留；随时恢复 |
| 交付 | 创建任务（复用会话 worktree/分支/目录），进入现有任务生命周期 |
| 删除 | 会话可弃（清理 worktree），不影响项目 |

## 4. skills 三级加载（用户确认的三种方式）

```
L1 角色按 tags 添加：
    角色配置页技能选择器增强 —— 按 tags 过滤/批量勾选
    （现有: 逐技能勾选 → 升级: 标签浏览 + 一键全选该标签）

L2 agent 辅助添加：
    创建/编辑角色时，调 pi（RPC 批处理）读取角色定义 + 技能库描述
    → 生成推荐技能集（依据: 角色职责描述 × 技能 tags/描述）
    → 一键采纳

L3 人工调整：
    在推荐结果上自由增删（保留现有手动勾选）
```

三个入口共存，L2 是增量智能层，不动现有数据模型（角色技能仍是勾选清单，只是"怎么填"更聪明）。

## 6. 架构含义

S1-S3 意味着 paihuo 需要一条"**会话执行通道**"（spawn pi RPC 进程 + JSONL 协议层 + 事件持久化），与现有 tmux 批处理通道并行：

- **pi 会话**：不套 tmux（RPC 是 stdio 协议，进程管理更干净；挂起=杀进程）
- **codex/claude 会话**：继续用 tmux（复用现有交互任务机制）
